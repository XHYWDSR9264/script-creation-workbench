# 剧本创作总控台：相似项目调研与融合决策

调研日期：2026-09-13

## 一、当前网站复核结论

当前 v0.6.0 已有项目隔离、素材/R2、正文不可覆盖版本、SHA-256、模型基础调用、结构审计、AI内部深审、人工放行、连续性账本、朱雀网页报告登记和 TXT/JSON 导出。它已经不是纯静态原型，但仍缺少真正的长任务执行层、正式 DOCX/PDF 包装和访问控制。

主要风险：

1. 在线预览为公开地址，尚无身份与项目权限隔离，不适合上传敏感或未授权原著。
2. 模型调用仍是同步请求；虽已留存运行状态和失败原因，但尚无队列级自动重试、暂停恢复与实时阶段进度。
3. AI内部深审已按 SOP V1.9 实现八维评分、核心维度底线、五张反查表和硬错误门槛，但结果仍必须人工确认，不能称为人工终审。
4. 朱雀记录已绑定某个正文版本，前端已区分“当前版本有效”与“历史版本失效”。
5. 已有按集、场、人物、地点的结构化导航；连续性账本的人工编辑和跨版本差异仍待补充。

## 二、相似项目及可迁移机制

### 1. Dify：模型提供商与文档输入分层

- 官方资料：https://docs.dify.ai/en/develop-plugin/features-and-specs/plugin-types/model-schema
- 官方资料：https://docs.dify.ai/en/guides/application-orchestrate/creating-an-application
- 值得借鉴：模型提供商适配层、凭据校验、文档提取节点、输入变量与工作流节点分离。
- 本项目采用：把“模型配置”“素材提取”“SOP领域提示词”“写入正文版本”拆成不同层；不把中转站兼容问题散落在页面代码里。
- 不直接引入：Dify整套服务过重，无法替代短剧专用SOP和交付规则。

### 2. LangGraph：检查点、人工中断与历史分叉

- 官方资料：https://docs.langchain.com/oss/python/langgraph/persistence
- 官方资料：https://docs.langchain.com/oss/python/langchain/human-in-the-loop
- 官方资料：https://docs.langchain.com/oss/python/langgraph/use-time-travel
- 值得借鉴：每一步保存检查点；需要人工判断时暂停；批准、编辑、拒绝后再继续；从历史节点重试时生成分支，不覆盖原历史。
- 本项目采用：任务运行记录、正文不可覆盖版本、G0—G6人工放行记录、失败后基于原输入重试。
- 不直接引入：当前部署在Cloudflare Workers，先用D1/Cloudflare Workflows实现同类语义，避免额外维护Python图运行时。

### 3. n8n：执行历史与失败重试

- 官方资料：https://docs.n8n.io/workflows/executions/all-executions/
- 值得借鉴：按运行状态过滤、保存失败上下文、可用原工作流或当前工作流重试。
- 本项目采用：每次模型任务生成独立 run_id，记录输入任务、阶段、状态、结果/错误和关联版本；后续提供“按原配置重试/按当前SOP重试”。

### 4. Cloudflare Workflows / Queues：当前技术栈的长任务底座

- 官方资料：https://developers.cloudflare.com/workflows/
- 官方资料：https://developers.cloudflare.com/queues/configuration/configure-queues/
- 值得借鉴：持久多步骤执行、自动重试、等待外部审批、队列削峰和死信处理。
- 本项目采用计划：模型生成、深审、朱雀轮询、DOCX/PDF打包分别成为可恢复步骤；前端只轮询任务状态或接收SSE，不再让一个HTTP请求承担完整长任务。

### 5. novelWriter：项目树与故事元素索引

- 官方资料：https://novelwriter.io/_downloads/054301b1f786f1540d800532b9f66576/novelWriter-2.8.pdf
- 值得借鉴：章节/场景树、人物/地点/情节资料、状态和重要性标签、字数统计、按人物线索查看出现位置。
- 本项目采用：从短剧正文解析“集—场—人物—地点”，形成场景导航、人物出场统计和连续性账本入口。

### 6. Beat / OpenDraft / Fountain：正文编辑和版本体验

- Beat：https://github.com/lmparppei/Beat
- OpenDraft：https://github.com/Proteus-Technologies-Private-Limited/OpenDraft
- Fountain：https://github.com/nyousefi/Fountain
- 值得借鉴：场景导航、自动场号、人物自动完成、卡片/时间线、版本对比、开放纯文本格式。
- 许可边界：Beat为GPL，不复制其代码；OpenDraft和Fountain即使许可更宽松，本项目本轮只借鉴产品机制，仍自行实现中文短剧解析规则。

### 7. Cloudflare Access：公开预览转内部生产站

- 官方资料：https://developers.cloudflare.com/workers/configuration/cloudflare-access/
- 值得借鉴：认证发生在请求到达Worker之前，可同时保护workers.dev、预览和自定义域。
- 本项目采用计划：上线真实客户素材前启用Access；未启用前页面持续显示公开预览警告。

## 三、融合优先级

### P0：必须先补

1. 持久任务运行记录、错误状态和重试基础。
2. SOP八维评分、五张反查表、硬错误与正文SHA绑定，明确为“AI内部深审”。
3. 朱雀报告仅在其绑定版本仍为当前版本时计入当前门禁。
4. 场景/人物/地点解析与导航。
5. 公开预览安全提示；正式投入使用前启用Cloudflare Access。

### P1：随后补

1. Cloudflare Workflows长任务、自动重试和人工中断。
2. G0—G6人工批准/驳回记录及前置条件。
3. DOCX/PDF在线解析、老王/大麦正式包装和WPS渲染复核。
4. 朱雀官方API适配器和异步任务轮询。

## 四、结论

不建议直接把Dify、n8n或任一编剧软件整体嵌进来。最佳路线是保持现有轻量Cloudflare架构，吸收它们经过验证的机制：Dify的模型适配、LangGraph的检查点与人工放行、n8n的执行历史、Cloudflare Workflows的持久任务、novelWriter/OpenDraft的场景与版本体验，再由本项目自己的短剧SOP V1.9负责领域判断。

## 五、本轮已落地的融合项

1. 采用 LangGraph 式“版本不可覆盖 + 人工批准/驳回”：G2—G6批准绑定最新正文版本，G4必须通过当前版本AI内部深审，G5必须通过当前版本真实朱雀报告，G6必须先满足G4/G5。
2. 采用 n8n 式运行历史：模型生成和AI深审生成独立 `run_id`，记录运行阶段、进度、成功/失败、错误和关联版本；当前是可追溯记录，不冒充异步实时进度。
3. 采用 novelWriter/OpenDraft 式场景导航：解析阿拉伯数字或中文数字集标题，以及场号、人物行和地点，生成“集—场—人物—地点”树。
4. 将SOP八维评分、三项核心底线、五张反查表和硬错误写入独立审计报告；分数由各维相加，不接受模型直接给出的总分。
5. 朱雀和审计报告增加当前版本状态：正文一旦保存为新版本，旧报告保留但自动标成“历史·已失效”。
6. 新建项目可配置单集时长、内容质量门槛和朱雀门槛；在线公开站增加敏感素材警告。
7. v0.6继续吸收n8n和novelWriter类机制：失败运行可在当前浏览器重新提供模型配置后按原指令重试，并记录原运行ID；连续性账本可从当前正文提取人物/地点，同时允许人工登记道具、时间线、权限和状态变化。
